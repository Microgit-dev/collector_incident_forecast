# Интеграции: системы заказчика, эмуляторы стенда и погода

Методика интеграций (ТЗ §6, §10, §13). Системы заказчика подключаются только на чтение. Единственное
исключение — передача утверждённой заявки в систему заявок.

**Боевые адаптеры и эмуляторы.** Для каждой системы заказчика написан адаптер под её протокол.
Режим задаётся в `.env`: `mock` / `emulated` — эмулятор стенда, боевой режим — система заказчика,
`off` — выключено. Код при подключении не меняется.

| Система | Режимы | Адаптер | На стенде |
|---|---|---|---|
| СМВУ | Kafka | консьюмер `consume_events`, внешний слушатель для шлюза | воспроизведение журналов, симулятор датчиков |
| LDAP / AD | LDAP, LDAPS, StartTLS | `django-auth-ldap`, группы → роли | тестовый OpenLDAP |
| Система учёта заявок | `mock`, `rest`, `off` | `HelpdeskClient`: токен, пути, карта статусов | `mock-helpdesk` |
| Реестр оборудования | `emulated`, `api`, `file` | `RegistryClient` и загрузка CSV/XLSX | эмуляция по каналам |
| Видеонаблюдение | `mock`, `http`, `off` | `VideoClient`: кадр на момент, ссылка на поток | `mock-vms` |
| Метеоданные | Open-Meteo | `WeatherClient` | настоящий открытый API |

**Страница «Интеграции»** у администратора показывает по каждой системе:
- режим (эмуляция или боевой);
- адрес;
- последний успешный обмен и последнюю ошибку.

Там же кнопки «Проверить связь» (запрос только на чтение) и ручная синхронизация. Итоги обмена
записывают сами клиенты: передача заявки, опрос статусов, кадр камеры, синхронизация реестра.

## Система учёта заявок (help desk)

У заказчика заявки ведутся в собственном help desk на Django. В стенде его заменяет эмулятор
`mock-helpdesk` (`infra/mock-helpdesk/app.py`). Он написан на стандартной библиотеке Python и хранит
данные в SQLite. Его страница — `https://localhost/helpdesk/`: так заявки видит сам help desk.

**Путь заявки:**

| Где | Статусы |
|---|---|
| Система прогнозирования | черновик → утверждена → передана в систему заявок |
| Help desk | принята → назначена бригада → в работе → выполнена (с отчётом исполнителя) → закрыта |

- **Передача.** Переход «Передать в систему заявок» отправляет заявку в help desk: номер, вид работ,
  приоритет, объект, срок, обоснование. Help desk присваивает свой номер (`HD-000001`). Если он
  недоступен, заявка остаётся утверждённой, а пользователь видит ошибку.
- **Синхронизация.** Раз в минуту (или по кнопке «Обновить из системы заявок») статусы забираются
  пачкой. Наша заявка двигается только вперёд: «назначена» остаётся «передана», «в работе» — «в работе»,
  «выполнена» и «закрыта» — «выполнена». Опрос идёт до закрытия заявки в help desk.
- **Что видно у нас.** В списке заявок: номер и статус в help desk, бригада, путь с временем каждой
  стадии, отчёт исполнителя. В хронологию карточки инцидента пишутся передача, начало работ и
  выполнение с отчётом. Рекомендация по ТО, из которой создана заявка, отмечается выполненной.

**Эмулятор.** Стадии идут по времени от создания. Переменная `HELPDESK_STAGE_MINUTES` (по умолчанию
2, 5, 20 и 10 минут) задаёт паузы между стадиями. Критические заявки проходят их вдвое быстрее,
низкие — вдвое медленнее. Для демонстрации заявку можно продвинуть кнопкой «Следующая стадия» на
странице help desk или запросом `POST /api/tickets/<id>/advance/`. Бригада подбирается по виду работ,
отчёт исполнителя — по шаблону вида работ.

**Подключение help desk заказчика** (`HELPDESK_MODE=rest`) задаётся переменными:

| Переменная | Что задаёт |
|---|---|
| `HELPDESK_URL` | адрес системы |
| `HELPDESK_TOKEN`, `HELPDESK_AUTH_SCHEME` | авторизация: `Bearer`, `Token` или `Basic` (в токене `логин:пароль`) |
| `HELPDESK_SUBMIT_PATH`, `HELPDESK_STATUS_PATH` | пути передачи заявки и чтения статусов пачкой |
| `HELPDESK_STATUS_MAP` | статусы заказчика → наши, JSON: `{"Исполнено": "done", "В работе": "in_progress"}` |
| `HELPDESK_CA_CERT` | корневой сертификат ЦС заказчика |

Контракт: передача возвращает `{"id", "status", "status_label", "assignee", "history", "report"}`,
чтение статусов — словарь по номерам. Если API заказчика устроено иначе, меняется только
`HelpdeskClient`.

`HELPDESK_MODE=off` — передачи нет: заявка остаётся в системе, бригада сама отмечает «в работе» и
«выполнена».

## Реестр оборудования

У заказчика реестра в цифровом виде пока нет, поэтому на стенде он эмулирован по каналам
(`REGISTRY_MODE=emulated`). Средние наработки на отказ и регламентные интервалы взяты из открытых
источников. Реестр заказчика подключается двумя способами:

- **API учётной системы** (`REGISTRY_MODE=api`, `REGISTRY_URL`, `REGISTRY_TOKEN`) — раз в сутки
  и по кнопке на странице «Интеграции». Ответ — список единиц или страницы
  `{"results": [...], "next": url}`.
- **Файл** CSV или XLSX — страница «Интеграции» или «Реестр оборудования» (инженер ТО, администратор).
  Шаблон файла скачивается там же.

Поля строки: `inventory_number` (ключ), `name`, `kind`, `object_id` (ид_объект из справочника)
или `object` (название), `picket`, `commissioned_at`, `last_maintenance_at`,
`maintenance_interval_days`, `mtbf_hours`, `channel_ids`, `is_active`. Правила загрузки
(`apps/assets/registry_sync.py`):

- записи реестра получают источник «реестр заказчика»; эмулированные удаляются при первой успешной
  загрузке;
- записи, заведённые вручную, не перезаписываются;
- единица, пропавшая из полного реестра, выводится из эксплуатации, а не удаляется: на неё ссылаются
  заявки и осмотры;
- дата ТО из реестра не откатывает более позднее ТО, отмеченное бригадой в системе;
- ошибки строк (нет объекта, неизвестный вид, неверная дата) не останавливают загрузку, а
  возвращаются списком.

Фактическое состояние оборудования ведётся в системе: бригада отмечает его при выполнении заявки,
инженер ТО — при осмотре (история в «Реестре оборудования»).

## Видеонаблюдение

Шаг 4 сценария ТЗ §12 — верификация, «при необходимости используя камеры наблюдения». В карточке
инцидента и прогноза пожара или НСД есть блок «Проверка по камерам»:

- **Ближайшие камеры.** Сначала камеры объекта тревоги и его частей, если их нет — объекта верхнего
  уровня. Порядок — по расстоянию в пикетах от канала тревоги. Камеры вне зоны пользователя не
  показываются.
- **Кадр.** Кадр на момент тревоги из архива системы видеонаблюдения или текущий. Бэкенд берёт кадр
  по API (`VideoClient`) и отдаёт интерфейсу. Браузеру не нужен доступ к системе видеонаблюдения,
  а CSP интерфейса не расширяется. Принимаются только изображения.
- **Запись в журнал.** Просмотр пишется в журнал действий и в хронологию карточки («Проверка по
  камере …»). Повторные обновления той же камеры в течение 10 минут не дублируются.
- **Поток.** Кнопка «Открыть в системе видеонаблюдения» — ссылка по шаблону `VMS_LIVE_URL`.

Реестр камер — `assets.Camera`: объект, пикет, ид камеры в VMS; ведётся в администрировании. На
стенде камеры расставлены командой `seed_cameras`: у входов, где стоят датчики дверей и люков, и
вдоль трассы. Эмулятор `mock-vms` (`infra/mock-vms/app.py`, стандартная библиотека Python) отдаёт
синтетический кадр тоннеля со штампом камеры и времени. Страница просмотра —
`https://localhost/vms/live/<ид>`.

Подключение VMS заказчика (`VMS_MODE=http`):

| Переменная | Что задаёт |
|---|---|
| `VMS_URL`, `VMS_TOKEN` | адрес и токен |
| `VMS_SNAPSHOT_PATH` | путь кадра, по умолчанию `/api/cameras/{id}/snapshot` с параметром `at` |
| `VMS_LIVE_URL` | ссылка для браузера на поток или архив (`{id}`, `{at}`) |
| `VMS_CA_CERT` | корневой сертификат ЦС заказчика |

## Grafana и Prometheus

Открываются из меню системы под учётной записью пользователя, без отдельных паролей:

- Интерфейс вызывает `POST /api/v1/observability/session/`. Бэкенд ставит подписанную cookie на
  8 часов (`HttpOnly`, `Secure`, `SameSite=Lax`).
- Перед каждым запросом к `/grafana/` и `/prometheus/` Caddy спрашивает бэкенд (`forward_auth`).
  Бэкенд проверяет подпись, активность учётки и право роли и возвращает заголовки `X-WEBAUTH-*`.
  По ним Grafana входит пользователя (`auth.proxy`) с ролью Admin или Viewer.
- Заголовки `X-WEBAUTH-*` от клиента Caddy удаляет до проверки, поэтому подделать вход ими нельзя.
- Выход из системы удаляет cookie. Снятая роль или заблокированная учётка теряют доступ не позже
  чем через 30 секунд.

| Роль | Grafana | Prometheus |
|---|---|---|
| Аналитик (`accounts.view_grafana`) | Viewer, папка «Аналитика» (бизнес-панели) | нет |
| Администратор (`accounts.view_system_monitoring`) | Admin, папки «Аналитика» и «Система» | да |

Права папок выставляет сервис `grafana-init` (`manage.py grafana_setup`), он же делает бизнес-панель
домашней. Источник TimescaleDB подключён ролью только для чтения `grafana_reader`
(`manage.py ensure_grafana_reader`): Viewer в Grafana может отправить в источник произвольный SQL,
поэтому роль видит только таблицы панелей, из учётных записей — только ФИО, транзакции только на
чтение, таймаут запроса 30 секунд.

## Погода (Open-Meteo)

Open-Meteo — открытый API без ключа. Погода берётся по центру Москвы:

- **история** — архив ERA5 (`load_weather --from 2019-01-01 --to …`): осадки, дождь, снег, средняя и
  максимальная температура, снежный покров за сутки;
- **последние 10 суток и прогноз на 3 суток** — прогнозный API, раз в 6 часов (`sync_weather`).
  Будущие сутки помечаются как прогноз и потом заменяются фактом.

**Признаки модели подтопления.** Погода одна на все каналы в сутки, поэтому она присоединяется
по дню одной и той же функцией (`add_weather`) и при обучении, и в работе:

| Признак | Смысл |
|---|---|
| `wx_precip_1`, `wx_precip_3` | осадки за сутки и за 3 суток |
| `wx_precip_next` | осадки на следующие сутки: при обучении — факт, в работе — прогноз |
| `wx_thaw_3` | оттепель: сумма плюсовых максимумов температуры за 3 суток |
| `wx_melt_3` | таяние: убыль снежного покрова за 3 суток |
| `wx_snow_depth` | снежный покров |

**Результат — честно.** Модель переобучена на той же выборке и с тем же разбиением:

| Модель | PR-AUC, валидация 2025 | PR-AUC, тест 2026 | Высокий уровень на тесте: P / R |
|---|---|---|---|
| Без погоды | 0,534 | 0,179 | 0,15 / 0,46 |
| С погодой | 0,537 | 0,185 | 0,15 / 0,45 |

Прирост в пределах шума: у одной из прежних версий без погоды тест тоже был 0,185. Модель
использует оттепель (она в первой десятке признаков) и снежный покров, осадки почти не использует.
Причина — в событии: прогнозируются тревоги насосов АНС («Затоплен», «Работают все насосы»), а их
частота определяется прежде всего поведением самих станций. Для этого признаки прошлых тревог и
пусков насосов сильнее погоды.

Погода оставлена в модели: она не ухудшает качество, объясняет весенние эпизоды через оттепель и
таяние, а при появлении датчиков уровня воды станет полезнее. Модель с погодой стала активной по
обычному правилу «чемпион / претендент» — по валидации 2025 года.
