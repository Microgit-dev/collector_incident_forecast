# Конструктор источников и датчиков. Расширяемость

Как подключить новый датчик, шлюз или систему с собственным форматом без программиста (ТЗ §7
«форматы и способы обмена», §14 «интеграция в любые другие системы», §17–18 «возможность интеграции»).

## Три слоя

```
сообщение источника ──► шаблон формата ──► единое событие ──► профиль датчика ──► состояние, число
(JSON, CSV, строка)     (где канал, время,    RawEvent         (пороги, служебные     качество, аспект
                         значение, тревога)                     коды, правила)          ──► конвейер
```

1. **Шаблон формата** (конструктор, вкладка «Шаблоны формата») приводит сообщение к единому событию
   `RawEvent`: ид канала, время, сырое значение, признак тревоги, ид события.
2. **Профиль датчика** (вкладка «Профили датчиков») задаёт, как понимать значение: тип, единица,
   диапазон, дрейф нуля, пороги предупреждения и тревоги, направление, служебные коды (= неисправность),
   ожидаемый интервал сообщений и правила «текст или регулярное выражение → состояние» с аспектом.
   Тип датчика ссылается на профиль, каналу можно задать свой.
3. **Конвейер** один для всех источников: канал из справочника → нормализация → телеметрия →
   эпизоды, прогнозы, карточки. Он не различает, откуда пришло событие.

Так новый вид оборудования подключается записями, а не кодом. Код нужен только для совсем нового
протокола транспорта: адаптер в `ingestion/adapters`, контракт — тот же `RawEvent`.

## Шаблон формата

| Формат | Что задаётся |
|---|---|
| JSON | пути к полям через точку (`data.dev.id`, `items[0].v`); `items` — путь к массиву измерений, поля пакета доступны в измерении как `^.поле`; несколько JSON построчно (NDJSON) тоже принимаются |
| CSV | разделитель, заголовок или список колонок |
| Строка | регулярное выражение с именованными группами `(?P<channel>…)`, `(?P<value>…)` |

Поля события:

| Поле | Значение |
|---|---|
| `channel` | путь к ид канала или константа `=80000001` |
| `channel_map` | ключ из сообщения → ид канала: `{"temp": 80000001, "hum": 80000002}` |
| `ts`, `ts_format`, `timezone` | время (путь или список путей для даты и времени), формат `iso`, `epoch_s`, `epoch_ms` или `strptime`, пояс для времени без смещения (по умолчанию Москва); без `ts` — время приёма |
| `value` | путь к значению (текст или число — понимает профиль) |
| `alarm` | признак тревоги: 1/0, t/f, true/false, да/нет |
| `event_id` | ид события; без него — стабильный хеш канала, времени и значения, повторная доставка не дублирует показание |
| `measurements` | несколько измерений в одном сообщении, у каждого свои `value` и `channel` |

**Библиотека** — пять готовых шаблонов, с них удобно начинать:
- событие СМВУ в JSON (текущий формат Kafka);
- журнал СМВУ в CSV;
- шлюз с несколькими измерениями в пакете;
- текстовая строка контроллера «канал;дата время;значение;тревога»;
- датчик MQTT «T=21.3;H=45».

## Песочница

Вставьте пример сообщения и нажмите «Проверить». Система покажет:
- сколько событий получилось и какие ошибки в каких сообщениях (ошибка одного не останавливает остальные);
- для каждого события: канал (и заведён ли он в системе), время, сырое значение, тревогу и **результат
  нормализации** профилем канала — состояние, число, качество, аспект.

Если канал ещё не заведён, можно выбрать профиль и посмотреть, как он поймёт значения. Профиль
проверяется отдельно полем «Проверить значение».

## Приём событий

| Способ | Как |
|---|---|
| HTTP от шлюза | `POST /api/v1/ingestion/templates/<код>/events/` с заголовком `Authorization: Token <ключ источника>`, тело — сообщение в формате шаблона (до 1 МБ). Ответ 202 — число принятых событий и ошибки |
| Kafka | в тему событий СМВУ пишется обёртка `{"template": "<код>", "payload": "<сообщение>"}`; консьюмер разбирает её по шаблону |
| Файл | шаблон CSV подходит для пакетной загрузки журналов |

Ключ источника выдаётся при создании шаблона и меняется кнопкой «Новый ключ». Неактивный шаблон
события не принимает. Каналы с ид из сообщений заводятся в «Зоны и объекты» (новый датчик — ид от
80 000 001), тип датчика задаёт профиль. События неизвестных каналов конвейер пропускает и считает.

Проверено на стенде: строка «93198;28.09.2026 12:49:04;47,5;1» по HTTP → Kafka → консьюмер →
показание «тревога, 47,5» у канала «Темп. ВШ ПК473 ур.2».

## Права

- Шаблоны и профили ведёт аналитик (операция «Управление контрактами датчиков»); администратор — всё.
- Смотрят шаблоны те, у кого есть просмотр источников данных.
- Каждое создание, правка, удаление и смена ключа пишутся в журнал действий.

## Расширяемость системы в целом

| Что добавить | Как | Код |
|---|---|---|
| Датчик нового формата | шаблон формата + профиль | не нужен |
| Новый тип датчика | профиль и правила состояний, тип датчика в справочнике | не нужен |
| Вид оборудования и регламент ТО | запись регламента, вид в реестре | не нужен |
| Система заказчика (help desk, реестр, видеонаблюдение, AD) | режим и адрес в `.env` | не нужен |
| Новая задача прогноза | описание задачи в `forecasting/specs.py` (событие, признаки, выборка) на общем конвейере моделей | немного |
| Новый протокол транспорта | адаптер `ingestion/adapters` с тем же `RawEvent` | немного |
| Новый модуль | модуль Django с явными границами (модульный монолит) и роль или права в `roles.py` | да |
