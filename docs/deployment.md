# Развёртывание на серверах заказчика

Инструкция для администраторов заказчика: как установить систему на свой сервер, подключить её к
AD и потоку СМВУ, проверить и обновлять. Нужен опыт администрирования Linux и Docker.

Демо-стенд и контур заказчика собираются из одних и тех же образов, различаются только настройками:

| | Демо-стенд | Контур заказчика |
|---|---|---|
| Адрес | `https://localhost` | имя сервера в сети предприятия |
| Сертификат | внутренний ЦС Caddy | сертификат заказчика или внутренний ЦС Caddy |
| Вход | тестовый OpenLDAP и демо-учётки | AD заказчика |
| Поток СМВУ | воспроизведение журнала (`replay`) | шлюз СМВУ пишет в Kafka |
| Контуры зон и объектов | демо-привязка к зданиям OSM | задаются в редакторе «Зоны и объекты» |
| Система учёта заявок | эмулятор `mock-helpdesk` | эмулятор, пока нет адаптера help desk заказчика |

## 1. Что понадобится

**Сервер**

| Ресурс | Минимум | С запасом |
|---|---|---|
| Процессор | 4 ядра x86-64 | 8 ядер |
| Память | 8 ГБ | 16 ГБ |
| Диск | 40 ГБ SSD | 100 ГБ SSD, резервные копии — на отдельном хранилище |
| ОС | Linux x86-64 с Docker Engine 24+ и Compose v2 | |

Минимум проверен на стенде: полный импорт истории, прогноз и 20 одновременных пользователей.
Диск в основном занимают исходные журналы (около 14 ГБ), Parquet-архив (около 3 ГБ) и база
(около 2 ГБ плюс рост оперативного окна).

**От служб заказчика**

| Что | Для чего |
|---|---|
| DNS-имя сервера, например `forecast.corp.local` | адрес интерфейса |
| Сертификат и ключ для этого имени (PEM), либо согласие на внутренний ЦС Caddy | TLS |
| Сервисная учётная запись AD только на чтение и корневой сертификат ЦС для `ldaps://` | вход сотрудников |
| Группы AD под роли системы (раздел 4.3) | роли пользователей |
| Сетевой доступ шлюза СМВУ к серверу по порту 9094 | живой поток событий |
| Справочники и журналы СМВУ (CSV/XLSX) | стартовые данные и история для моделей |
| Решение по карте: свой сервер тайлов, доступ в интернет или карта без подложки | подложка карты мониторинга (раздел 6.3) |

**Сетевые порты сервера**

| Порт | Кто обращается | Назначение |
|---|---|---|
| 443 | пользователи | интерфейс, API, WebSocket, Grafana |
| 80 | пользователи | перенаправление на 443 |
| 8443 | пользователи учебного контура | учебный контур, если он включён |
| 9094 | только шлюз СМВУ | внешний слушатель Kafka |

База, Redis, Kafka (внутренний слушатель), Prometheus и экспортеры наружу не публикуются. Kafka UI
в контуре заказчика не запускается. Исходящие соединения системе не нужны. Исключения — по
решению заказчика: тайлы карты, Overpass и погода (раздел 6).

## 2. Доставка на сервер

### Вариант А: у сервера есть доступ в интернет

```bash
git clone <репозиторий> /opt/collector && cd /opt/collector
cp .env.example .env              # затем раздел 4
docker compose build              # 5–10 минут
```

### Вариант Б: закрытый контур

На машине с интернетом и Docker, из корня репозитория:

```bash
infra/deploy/bundle.sh dist/
```

Скрипт соберёт образы системы, скачает сторонние и сложит в `dist/`:
- `collector-images-<версия>.tar.gz` — все образы, около 2 ГБ;
- `collector-src-<версия>.tar.gz` — файлы развёртывания: compose, `infra/`, полигон учебного
  контура, документация;
- `SHA256SUMS` — контрольные суммы.

На сервере:

```bash
sha256sum -c SHA256SUMS
mkdir -p /opt/collector && tar xzf collector-src-<версия>.tar.gz -C /opt/collector
docker load -i collector-images-<версия>.tar.gz
cd /opt/collector && cp .env.example .env
```

Образы системы помечены тегом `:local` и никогда не скачиваются из реестра. Сторонние образы
после `docker load` уже есть на сервере, поэтому compose их тоже не скачивает.

## 3. Состав каталога на сервере

| Путь | Что | Резервировать |
|---|---|---|
| `.env` | настройки и секреты | да, отдельно от копий базы |
| `data/` | справочники и журналы заказчика, монтируются только на чтение | исходники хранятся у заказчика |
| `artifacts/` | модели и Parquet-архив | да |
| `backups/` | ежедневные копии базы | копировать на отдельное хранилище |
| `infra/caddy/certs/` | сертификат и ключ сайта | да |
| `infra/deploy/certs/` | корневой сертификат ЦС для AD | да |

## 4. Настройка

Все настройки — в `.env`. Файлы compose и Caddyfile править не нужно.

### 4.1 Обязательные

| Переменная | Значение |
|---|---|
| `COMPOSE_FILE` | `docker-compose.yml:infra/deploy/docker-compose.customer.yml` — все команды `docker compose` подхватят настройки контура заказчика |
| `SECRET_KEY` | случайная строка от 64 символов: `python3 -c "import secrets; print(secrets.token_urlsafe(64))"` |
| `DEBUG` | `false` |
| `DEMO_USERS` | `false` — без демо-команд, демо-сотрудников и демо-привязки к карте |
| `DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_PASSWORD` | первый администратор, локальная учётная запись на случай недоступности AD |
| `POSTGRES_PASSWORD` и тот же пароль в `DATABASE_URL` | пароль базы |
| `GRAFANA_ADMIN_PASSWORD` | пароль Grafana |

С `DEMO_USERS=false` и ключом по умолчанию система не запустится: это защитная проверка
`collector.S001`.

### 4.2 Адрес и сертификат

| Переменная | Пример |
|---|---|
| `SITE_ADDRESS` | `forecast.corp.local` |
| `ALLOWED_HOSTS` | `forecast.corp.local` (внутренние имена `localhost` и `backend` для проверок добавляются сами) |
| `CSRF_TRUSTED_ORIGINS` | `https://forecast.corp.local` |
| `COMBAT_URL` | `https://forecast.corp.local` |
| `TLS` | `internal` или `/certs/fullchain.pem /certs/privkey.pem` |

Сертификат заказчика: файлы `fullchain.pem` (сертификат с цепочкой) и `privkey.pem` кладутся в
`infra/caddy/certs/` и указываются в `TLS`. При `TLS=internal` Caddy выпускает сертификат своим
ЦС. Тогда корневой сертификат из тома `caddydata` (`/data/caddy/pki/authorities/local/root.crt`)
раздаётся на рабочие места через групповые политики. Сертификат должен покрывать `SITE_ADDRESS`,
а если включён учебный контур — то же имя на порту 8443.

### 4.3 Вход через AD

| Переменная | Пример для AD |
|---|---|
| `LDAP_ENABLED` | `true` |
| `LDAP_SERVER_URI` | `ldaps://dc01.corp.local:636` |
| `LDAP_CA_CERT` | `/certs/corp-ca.pem` — файл кладётся в `infra/deploy/certs/` |
| `LDAP_START_TLS` | `true`, если используется `ldap://` со StartTLS вместо `ldaps://` |
| `LDAP_BIND_DN`, `LDAP_BIND_PASSWORD` | сервисная учётная запись только на чтение |
| `LDAP_USER_BASE` | `OU=Users,DC=corp,DC=local` |
| `LDAP_USER_FILTER` | `(sAMAccountName=%(user)s)` |
| `LDAP_GROUP_BASE` | `OU=Forecast,OU=Groups,DC=corp,DC=local` — отдельная OU только с группами системы |
| `LDAP_GROUP_FILTER` | `(objectClass=group)` |
| `LDAP_GROUP_TYPE` | `ad` |

**Роли.** Роль пользователя определяется группой AD. Имя группы (`cn`) должно совпадать с кодом
роли:

| Группа AD | Роль |
|---|---|
| `admin` | Администратор |
| `head` | Руководитель подразделения |
| `ods_dispatcher` | Диспетчер ОДС |
| `unit_dispatcher` | Диспетчер подразделения |
| `analyst` | Аналитик |
| `technician` | Ремонтная бригада |
| `observer` | Наблюдатель |

Группы при каждом входе переносятся в систему как есть. Поэтому `LDAP_GROUP_BASE` должен указывать на
OU, где лежат только эти семь групп, иначе в систему попадут все группы сотрудника.

**Команда и зона.** Атрибут `department` (или `departmentNumber`) учётной записи — код команды в
системе. При входе сотрудник попадает в эту команду и получает её зону ответственности. Если
атрибут не заполнен, команда и зона назначаются вручную в разделе «Зоны и объекты» → «Сотрудники».

**Защита от подбора.** После 5 неудачных попыток вход блокируется на 15 минут. Блокировка работает
и для AD: система не передаёт пароль в AD, пока учётная запись заблокирована, поэтому политика
блокировки домена не срабатывает от атак на систему.

### 4.4 Поток СМВУ

| Переменная | Значение |
|---|---|
| `KAFKA_EXTERNAL_HOST` | имя или IP сервера, по которому к нему обращается шлюз СМВУ |
| `KAFKA_EXTERNAL_BIND` | IP интерфейса, смотрящего в сеть СМВУ (по умолчанию `127.0.0.1` — слушатель закрыт) |
| `KAFKA_TOPIC_RAW_EVENTS` | `smvu.raw-events` |

Формат события и проверка — в разделе 6.1.

### 4.5 Карта, погода, заявки

| Переменная | Значение |
|---|---|
| `MAP_STYLE_LIGHT`, `MAP_STYLE_DARK` | адреса стилей подложки; пусто — карта без подложки |
| `MAP_TILES_ORIGIN` | адрес сервера тайлов для CSP, например `https://tiles.corp.local` |
| `OVERPASS_URL` | адрес Overpass API; пусто — автовыделение зданий выключено |
| `WEATHER_URL` | Open-Meteo; без интернета задача погоды выключается (раздел 6.4) |
| `HELPDESK_URL` | эмулятор `http://mock-helpdesk:8080` (раздел 6.5) |

## 5. Первый запуск

```bash
docker compose up -d
docker compose logs -f migrate    # ждать «bootstrap done», 1–3 минуты
infra/deploy/check.sh https://forecast.corp.local
```

При первом запуске одноразовый контейнер `migrate`:
- применяет миграции базы;
- создаёт роли и права, таксономию состояний, политики эскалации, уровни риска, справочник причин
  решений, правила разметки, расписания и статьи вики;
- загружает справочники объектов и каналов, если они лежат в `data/dataset/`;
- создаёт первого администратора.

Все шаги идемпотентны: повторный запуск ничего не дублирует и не затирает правки.

**Проверка.** Скрипт `check.sh` только читает состояние и ничего не меняет. Что он проверяет:
- все контейнеры работают;
- `migrate` завершился успешно;
- проверки безопасности Django без ошибок;
- интерфейс и API отвечают;
- есть заголовки безопасности;
- сертификат выдан на нужное имя.

Все строки должны быть `[ ok ]`.

### 5.1 Данные

Справочники кладутся в `data/dataset/`, журналы — в `data/dataset/journals/`, в том же формате, что
выгрузка для стенда. Дальше — из интерфейса («Загрузка данных», роль «Аналитик» или
«Администратор») или из консоли:

```bash
docker compose run --rm backend python manage.py import_history            # все годы, кроме 2021
docker compose exec worker python manage.py train_model --task gas          # и --task flood
docker compose exec worker python manage.py forecast
```

Импорт занимает 1–2 минуты на год журнала, пиковая память — около 2,3 ГБ. После импорта модель
отказа датчиков обучается автоматически (модели газа и подтопления — командами выше), дальше прогноз пересчитывается каждые 15 минут.

### 5.2 Структура и люди

Администратор или руководитель района:
1. **Команды** (админка → «Команды»): коды команд совпадают с атрибутом `department` в AD.
2. **Зоны ответственности** («Зоны и объекты» → «Зоны»): граница на карте, цвет, смежные зоны.
3. **Объекты на карте** («Зоны и объекты» → «Объекты»): у каждого объекта из справочника задаётся
   контур. Щелчок по зданию выделяет контур автоматически (если подключена подложка или Overpass),
   иначе контур обводится вручную. В справочниках заказчика координат нет, поэтому это
   обязательный шаг для карты мониторинга.
4. **Сотрудники** входят под своими учётными записями AD и сразу получают роль и зону. Недостающее
   назначается на вкладке «Сотрудники».

Схема по пикетам, прогнозы и карточки работают и без контуров: они нужны только для карты.

## 6. Подключение источников

### 6.1 Поток СМВУ

Шлюз СМВУ публикует события в Kafka `KAFKA_EXTERNAL_HOST:9094`, тему `smvu.raw-events`. Одно
сообщение — одно событие канала в JSON (UTF-8). Ключ сообщения — ид канала:

```json
{"event_id": 1048576, "channel_external_id": 10234, "ts": "2026-09-26T14:05:31+03:00",
 "raw_value": "0.8", "raw_alarm": false, "source": "smvu"}
```

| Поле | Смысл |
|---|---|
| `event_id` | уникальный номер события в СМВУ (повторная доставка не создаёт дублей) |
| `channel_external_id` | ид канала из справочника каналов |
| `ts` | время события с часовым поясом |
| `raw_value` | «сырое» значение как в журнале СМВУ; служебные коды распознаются профилями нормализации |
| `raw_alarm` | признак тревоги, если СМВУ его передаёт |

Проверка: в Grafana (системный дашборд) растёт число принятых событий, а задержка потока
держится в пределах секунд. Журнал приёма: `docker compose logs -f consumer`.

Слушатель 9094 без шифрования. Доступ к нему открывается на межсетевом экране только для адреса
шлюза. Если политика заказчика требует TLS или SASL на этом участке, слушатель `EXTERNAL`
в `infra/deploy/docker-compose.customer.yml` переводится на `SSL` или `SASL_SSL`.

### 6.2 Справочники

Новые объекты и каналы подгружаются повторной загрузкой справочников из интерфейса. Существующие
записи обновляются, контуры и назначения не затираются.

### 6.3 Карта мониторинга в закрытом контуре

Подложка — векторные тайлы OpenStreetMap, их запрашивает браузер пользователя. Варианты:

| Вариант | Что сделать |
|---|---|
| Свой сервер тайлов (рекомендуется) | развернуть сервер векторных тайлов OSM в формате MapLibre (например, VersaTiles с выгрузкой по Москве), указать `MAP_STYLE_LIGHT/DARK` и `MAP_TILES_ORIGIN` |
| Доступ рабочих мест к `tiles.versatiles.org` | оставить значения по умолчанию |
| Без подложки | оставить `MAP_STYLE_LIGHT/DARK` пустыми: зоны, объекты, бейджи и датчики на пустом фоне |

Автовыделение здания берёт контур прямо из подложки, поэтому со своим сервером тайлов оно
работает без Overpass. Overpass (`OVERPASS_URL`) — запасной путь, его запросы идут с сервера.
Если подложки нет, контуры объектов обводятся вручную.

После изменения этих переменных выполните `docker compose up -d`: пересоздадутся контейнеры с
изменённым окружением.

### 6.4 Погода

Погоду раз в 6 часов загружает задача «Погода Open-Meteo» — ей нужен доступ сервера к
`archive-api.open-meteo.com`. Без интернета задача выключается в админке: «Periodic tasks» →
снять «Enabled». Модели работают и без погоды, прирост от неё в пределах шума.

### 6.5 Система учёта заявок

Адаптер help desk заказчика не разрабатывался: систему и её API на этапе MVP не предоставили.
Контур работает с эмулятором `mock-helpdesk`. Для подключения нужен адаптер по API help desk
заказчика: клиент в `backend/apps/integrations/` с теми же операциями (передать заявку, прочитать
статус и отчёт исполнителя), адрес — в `HELPDESK_URL`.

## 7. Учебный контур

Отдельная база, Redis, тема Kafka и help desk. Боевые данные он не видит:

```bash
# в .env: TRAINING_ADDRESS=forecast.corp.local:8443, TRAINING_URL=https://forecast.corp.local:8443
docker compose --profile training up -d
```

Симулятор датчиков слушает только `127.0.0.1:8095`. Удалённо к нему подключаются через
SSH-туннель: `ssh -L 8095:127.0.0.1:8095 <сервер>`.

## 8. Обновление

```bash
cd /opt/collector
docker compose exec backup /backup.sh                     # внеплановая копия базы
for i in backend web mock-helpdesk simulator; do           # метка для отката
  docker tag collector-forecast/$i:local collector-forecast/$i:prev
done
# вариант А: git pull && docker compose build
# вариант Б: docker load -i collector-images-<новая версия>.tar.gz и распаковать collector-src поверх
docker compose up -d                                      # migrate применит новые миграции
infra/deploy/check.sh https://forecast.corp.local
```

Перерыв в работе — около минуты, пока пересоздаются контейнеры. Сторонние образы меняются только
вместе с версией системы.

**Откат:** вернуть метки `:prev` → `:local`, выполнить `docker compose up -d`. Если новая версия
применила миграции, базу восстанавливают из копии, сделанной перед обновлением. Порядок
восстановления — в главе «Резервное копирование и восстановление» сопроводительной документации.

## 9. Эксплуатация

- **Резервные копии.** Контейнер `backup` каждые сутки делает `pg_dump` в `backups/` и хранит
  7 дневных, 4 недельных и 3 месячных копии. Каталоги `backups/`, `artifacts/` и `.env` копируются
  на отдельное хранилище средствами заказчика. Раз в квартал — пробное восстановление.
- **Мониторинг.** Grafana — `https://<сервер>/grafana/`: системный дашборд (контейнеры, база,
  поток, очереди) и «Бизнес-показатели». Prometheus хранит метрики 15 суток.
- **Журналы контейнеров:** `docker compose logs --since 1h <сервис>`. Журнал действий
  пользователей — в админке, «Журнал действий».
- **Расписание задач** меняется в админке («Periodic tasks») без перезапуска.
- **Автозапуск.** Все сервисы с `restart: unless-stopped` поднимаются вместе с Docker после
  перезагрузки сервера. Нужно, чтобы сама служба Docker была включена: `systemctl enable docker`.

## 10. Типичные проблемы

| Признак | Причина и решение |
|---|---|
| `migrate` завершился с ошибкой `collector.S001` | ключ по умолчанию при `DEMO_USERS=false` — задать `SECRET_KEY` |
| Браузер: «Bad Request (400)» | имени сервера нет в `ALLOWED_HOSTS` |
| Вход работает, но формы админки отвечают «CSRF verification failed» | адреса нет в `CSRF_TRUSTED_ORIGINS` |
| Сотрудник AD входит, но меню почти пустое | нет группы-роли: проверить членство в группе из раздела 4.3 и `LDAP_GROUP_BASE` |
| Вход через AD не проходит, в журнале backend `SERVER_DOWN` или `certificate verify failed` | нет доступа к контроллеру домена или не подключён `LDAP_CA_CERT` |
| «Слишком много попыток входа» | блокировка на 15 минут после 5 ошибок; снимается сама или командой `docker compose exec backend python manage.py unlock <логин>` (пишется в журнал действий) |
| Карта без подложки | нет доступа браузера к серверу тайлов или адрес не совпадает с `MAP_TILES_ORIGIN` (ошибка CSP видна в консоли браузера) |
| Новые события не появляются | шлюз не достучался до 9094 (межсетевой экран, `KAFKA_EXTERNAL_BIND`) или ид каналов нет в справочнике; смотреть `docker compose logs consumer` |
| `import_history` прерывается | мало памяти: нужно не меньше 8 ГБ для контейнеров |
| Интерфейс открывается, уведомления не приходят | прокси между пользователями и сервером режет WebSocket (`/ws/`) — разрешить Upgrade |

## 11. Перед вводом в эксплуатацию

Полный чек-лист с обоснованием — в отчёте по безопасности. Коротко:

1. `SECRET_KEY` случайный, `DEBUG=false`, `DEMO_USERS=false`, пароли базы, Grafana и
   администратора сменены.
2. `check.sh` — все строки `[ ok ]`.
3. Имя сервера и сертификат заказчика; корневой сертификат доверен на рабочих местах.
4. AD через `ldaps://` или StartTLS, сервисная учётная запись только на чтение, группы ролей
   в отдельной OU.
5. Порт 9094 открыт только для шлюза СМВУ, 443 и 8443 — только из сети предприятия или VPN.
6. Kafka UI и симулятор не опубликованы (в контуре заказчика Kafka UI не запускается).
7. Резервные копии уходят на отдельное хранилище и шифруются, пробное восстановление выполнено.
8. Решено, откуда карта берёт подложку, и настроены `MAP_*` и `OVERPASS_URL`.
9. Задача погоды выключена, если у сервера нет интернета.
