# Архитектура

## Принципы

1. **Модульный монолит.** Один деплой-артефакт и одна БД, но модули с явными границами.
   Любой модуль можно вынести в отдельный сервис: связи между модулями идут через сервисные функции
   и Django-сигналы, а не через чужие таблицы.
2. **Слои внутри модуля** (упрощённая clean architecture):
   - `domain/` — чистый Python без Django (движок нормализации, контракты моделей прогноза);
   - `services.py` — команды, меняющие состояние, с бизнес-правилами и транзакциями;
   - `selectors.py` — запросы на чтение;
   - `api/` — DRF: сериализаторы, вьюсеты, маршруты;
   - `models.py`, `admin.py`, `tasks.py` — Django ORM, админка, фоновые задачи Celery.
   ORM не оборачивается в собственные репозитории: это дало бы больше кода без пользы.
3. **Расширяемость через данные, а не через код.** Новый тип датчика — это профиль нормализации
   и правила. Новый формат сообщения — шаблон в конструкторе (JSON, CSV, строка по регулярному
   выражению), приём по HTTP с ключом или обёрткой в Kafka. Новый транспорт — адаптер в
   `ingestion/adapters` с тем же контрактом `RawEvent`. Системы заказчика подключаются режимом в
   `.env`. Подробно — глава «Конструктор источников и датчиков».
4. **Всё, что можно взять из Django, берём из Django:** auth, Groups/Permissions (RBAC), admin,
   сигналы, миграции.

## Модули

| Модуль | Ответственность |
|---|---|
| `core` | Базовые модели, права DRF, пагинация, health, команда `bootstrap` |
| `topology` | Дерево объектов (materialized path, treebeard), схематическая геометрия, **фильтр по зоне ответственности** |
| `accounts` | Пользователь с зоной ответственности, роли (`roles.py`), LDAP |
| `audit` | Журнал действий пользователей (middleware + явные бизнес-события), django-auditlog для истории изменений |
| `normalization` | Профили датчиков, правила состояний, движок `domain/engine.py` |
| `assets` | Реестр: типы датчиков, каналы, оборудование |
| `ingestion` | Адаптеры источников, шаблоны конструктора (`templates.py`, `constructor.py`), конвейер, Kafka-консьюмер, эмулятор потока, пакетный импорт |
| `telemetry` | Hypertable показаний, текущее состояние каналов, сигнал `channel_states_changed` |
| `forecasting` | Реестр моделей, политики риска, журнал прогнозов, обучение |
| `incidents` | Алерты, инциденты, решения, хронология, эскалация, реактивные правила |
| `workorders` | Рекомендации по ТО, заявки и их статусы, план ТО, осмотры, регламент, графики ТО и ТР и ППР (`schedules.py`) |
| `notifications` | Уведомления: БД + WebSocket (Channels) |
| `analytics` | Сводки и отчёты |
| `integrations` | Клиенты внешних систем с режимами (эмуляция / боевой): help desk, реестр оборудования, видеонаблюдение, погода; каталог интеграций с проверкой связи |

## Поток данных

```
СМВУ (эмуляция: replay журнала) ──Kafka smvu.raw-events──▶ consumer
Файлы CSV/XLSX ──ImportJob (Celery)──────────────────────▶ тот же Pipeline
    Pipeline: RawEvent → канал из справочника → профиль → normalize() → Reading (hypertable)
                                                                    → ChannelState (текущее)
    ChannelState изменился → сигнал → incidents.rules → raise_alert → Incident → notify (WS)
Celery beat → forecasting.run_forecast_cycle → Prediction → RiskPolicy → raise_alert
```

Доставка из Kafka — at-least-once: offset фиксируется после записи батча, дубли гасит
составной ключ `(ts, event_id)` в hypertable.

## Хранение (ТЗ §13)

| Контур | Реализация |
|---|---|
| Оперативный | Несжатые чанки hypertable `telemetry_reading` (7 дней на чанк), `telemetry_channelstate` |
| Архивный | Сжатие чанков старше 30 дней (segment by channel), Parquet для обучения моделей |
| Аналитические витрины | Continuous aggregate `telemetry_reading_hourly`, дальше — витрины в модуле `analytics` |

## Вертикаль управления

- **Роль** определяет, *что* пользователь может делать: Django Group + permissions (`accounts/roles.py`).
- **Зона ответственности** (`User.scope_node`) определяет, *где*: пользователь видит поддерево
  своего узла. Право `view_all_scopes` (ОДС, аналитик) снимает это ограничение.
- **Ответственный уровень инцидента** — ближайший вверх по дереву узел, к которому прикреплены люди.
  Если за время из `EscalationPolicy` никто не отреагировал, инцидент поднимается на уровень выше,
  а уведомление получает следующее звено.
- **Закрепление карточки.** Взявший инцидент диспетчер блокирует его для остальных.
  Забрать карточку может только роль с правом `takeover_incident`.

| Роль | Зона | Ключевые права |
|---|---|---|
| Администратор | вся | всё |
| Руководитель подразделения | своё поддерево | решения, эскалация, утверждение заявок, отчёты, журнал действий |
| Диспетчер ОДС | вся | квитирование, закрепление, решения, эскалация, черновики заявок |
| Диспетчер подразделения | своё поддерево | то же, что у ОДС, в своей зоне |
| Аналитик | вся | профили нормализации, модели и дообучение, верификация, отчёты |
| Ремонтная бригада | свои заявки | исполнение заявок |
| Наблюдатель | своё поддерево | только просмотр |

## Безопасность (ТЗ §11)

- TLS 1.2+ на Caddy (в стенде — локальный CA, в продуктиве — сертификат домена).
- Аутентификация: JWT для SPA и внешних клиентов API, сессии для админки. LDAP/AD через
  django-auth-ldap; в стенде работает тестовый OpenLDAP.
- RBAC + фильтр по зоне ответственности на уровне queryset: чужие объекты возвращают 404, а не 403.
- Журнал действий: каждый изменяющий запрос и бизнес-события пишутся в `ActionLog`,
  который нельзя изменить через админку. История изменений полей хранится в django-auditlog.
- Интеграции с системами заказчика работают только на чтение (`DataSource.read_only`).

## Надёжность и наблюдаемость

- Бэкап: ежедневный `pg_dump` с ротацией (контейнер `backup`, каталог `./backups`).
- Все сервисы с `restart: unless-stopped` и healthcheck, миграции выполняет одноразовый контейнер `migrate`.
- Метрики: django-prometheus (HTTP, БД), метрики консьюмера (задержка потока — требование ТЗ ≤ 300 с),
  Celery, PostgreSQL, Redis, Caddy. Готовый дашборд лежит в Grafana → Collector Forecast.
