# Аналитика: эффективность диспетчеров, качество прогнозов, отчёты

Методика аналитики (ТЗ §8, §9). Раздел «Аналитика» виден ролям с правом просмотра, каждый видит
свою зону ответственности. Выгружать отчёты могут руководитель, аналитик и администратор.

## Эффективность диспетчеров (§8)

Считается по карточкам, открытым за период:

| Показатель | Как считается |
|---|---|
| Карточек на смену | карточек за период / число 12-часовых смен |
| Сжатие потока | сигналов в карточках-фактах / число карточек-фактов |
| До просмотра | от открытия карточки до первого просмотра (журнал просмотров) |
| До взятия в работу | до события «взят в работу» |
| До решения | до первого решения диспетчера |
| Эскалации по таймауту | доля карточек, эскалированных из-за отсутствия реакции (ручные эскалации не считаются) |
| Закрыто с результатом | доля закрытых карточек, где указано «что произошло» или причина решения |
| Что происходило | распределение ответов «что произошло» (§12) |
| Помог ли прогноз | ответы по прогнозным карточкам |

Время указано медианой и 90-м процентилем. Среднее не используется: одна карточка, забытая на ночь,
искажает его. Те же показатели считаются по уровням и по сотрудникам.

Метрики сотрудника описывают поток карточек, а не качество работы человека. Например, доля
ложных срабатываний зависит от объектов в зоне ответственности.

## Качество прогнозов (§9)

Журнал на выбор: оперативный или бэктест. Показатели по каждой из пяти задач:

- **Точность** — доля подтвердившихся среди записей журнала (уровень «высокий» и выше) с известным
  исходом. **Доля ложных** — остальные записи. «Предотвращено» (диспетчер устранил причину по
  прогнозу) ошибкой не считается.
- **Полнота по факту** — сколько событий, начавшихся за период, заранее предупредил прогноз уровня
  «высокий» и выше. Событие определяется на суточной витрине по тому же правилу, что при обучении:
  в сутки d событие есть, а на конец суток d−1 канал был в норме. Условия заданы в спецификации
  задачи (`event_sql`, `healthy_sql` в `forecasting/specs.py`).
- **Нагрузка** — записей журнала в сутки.
- **Упреждение** и метрики на тесте — по активной модели (отложенный 2026 год).

Для пожара и НСД полнота не считается: подтверждённых событий в данных нет. Исход индикатора —
«угроза проявилась».

**Бэктест за июнь 2026 года** (прогноз раз в сутки):

| Задача | Точность | Полнота по факту | На тесте: точность / полнота |
|---|---|---|---|
| Отказ датчика | 20 % | 18 % (104 из 569 событий) | 21 % / 9 % |
| Загазованность | 13 % | 93 % (52 из 56) | 8 % / 74 % |
| Подтопление | 15 % | 43 % (36 из 84) | 15 % / 46 % |
| Пожар (индикатор) | 59 % | — | — |
| НСД (индикатор) | 37 % | — | — |

## Эмуляция смен

На стенде нет истории работы диспетчеров, а без неё метрики §8 пусты. Команда

```
python manage.py emulate_shifts --from 2026-06-16 --to 2026-06-30   # --clear — удалить эмуляцию
```

превращает **реальные эпизоды** из данных заказчика в карточки. Используется та же склейка сигналов
и те же гипотезы, что в работе. Дополнительно создаются прогнозные карточки по бэктесту уровней
«критический», а для газа, подтопления, пожара и НСД — ещё и «высокий». Демо-диспетчеры отрабатывают
карточки так:

- карточку объекта обычно берёт его диспетчер, остальные — дежурный ОДС (дневная и ночная смена);
- задержки случайные (логнормальные) и зависят от уровня, контура и ночного времени, у каждого
  сотрудника свой темп;
- если просмотра не было до таймаута реакции, карточка эскалируется;
- «что произошло» выбирается по гипотезам карточки с учётом их весов.

Всё созданное помечено «эмуляция»: в списке и в карточке стоит пометка, в аналитике и отчётах её
можно исключить. Метки для обучения моделей по эмулированным решениям не создаются.

На стенде 16–30.06.2026: 1 330 карточек (1 010 фактов и 320 прогнозных), 73 эскалации по таймауту.

## Отчёты PDF и XLSX

- **PDF** — сводка для руководства: нагрузка, скорость реакции по уровням, сотрудники, качество
  прогнозов, что происходило. Если в периоде есть эмуляция, об этом предупреждает отдельная строка.
- **XLSX** — та же сводка, плюс по суткам, журнал инцидентов (до 20 тыс. строк) и журнал прогнозов
  (до 50 тыс.).

Отчёт строится теми же функциями, что страница, поэтому цифры совпадают. Файлы хранятся на сервере
в списке «Мои отчёты». Формирование пишется в журнал действий.

## Бизнес-дашборд Grafana

«Бизнес-показатели: инциденты, диспетчеры, прогнозы»: 13 панелей по витринам TimescaleDB.
Переключатели «эмуляция смен» и «журнал прогнозов» (оперативный или бэктест). Дашборд
генерируется скриптом `infra/grafana/build_business.py`, JSON лежит в `infra/grafana/dashboards/`.
